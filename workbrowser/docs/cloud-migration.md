# 本番環境へ移行するための作業

最終更新: 2026-11-16。この資料は実装と確認の作業計画。デプロイ済みの構成や、そのまま実行できる完成済みデプロイ手順ではない。

## 1. 目標と現在地

開発はローカルサーバー、本番は会社のIAPで保護したCloud Runサーバーを使う。Workstationsは開発場所であり、社員向け本番サーバーとして利用する計画ではない。

```text
社員のChrome拡張
  └─ 会社アカウントでIAPを通過
       └─ Cloud Run API
            ├─ 実行用サービスアカウント → Vertex AI / Gemini
            ├─ 共有の管理設定ストア
            └─ 監査・利用量管理
```

ReActループとブラウザ操作は引き続き拡張内で動かす。Cloud Runはモデル通信・認証・管理設定を担当し、ブラウザを起動する必要はない。

現在の `server/index.ts` は `K_SERVICE` が設定された環境、または `AUTH_MODE` がlocal以外の環境では起動を拒否する。`AUTH_MODE=iap` を設定するだけで本番対応にはならない。拡張の接続先もloopback限定なので、以下の実装が必要。

## 2. 先に決める会社固有の値

| 項目 | 決める内容 |
| --- | --- |
| 対象社員 | Workspace組織、複数ドメインの扱い、退職・停止時のアクセス失効 |
| 利用規模 | 当初想定は約200人。実際の同時利用数、モデル利用枠、費用上限 |
| 拡張配布 | 固定拡張ID、ChromeOSを含む配布先、管理対象Chromeのポリシー |
| サーバー | Cloud Runのproject、region、service、会社用HTTPS URL |
| IAP | Cloud Run直接保護かロードバランサー方式か、audience、利用者のアクセス許可 |
| OAuth | 拡張で利用できる認証方式、client ID、許可するリダイレクト先、programmatic access |
| モデル | Vertex AI project、location、関数呼び出し対応モデルID |
| 実行主体 | Cloud Run用サービスアカウントと必要な権限 |
| 管理者 | サイト・AI送信許可・実行上限を変更できる管理者の指定方法 |
| データ | サイト・データ分類・保管・監査についての会社ルール |

Googleグループを必須としない方針を維持し、組織の利用者と管理者指定の方法を決める。IAPを利用できることと、Workbrowserの管理APIを使えることは別の権限として検証する。

## 3. 拡張からIAPへ接続する

対象: [api.ts](../src/extension/api.ts)、[background.ts](../entrypoints/background.ts)、[設定画面](../entrypoints/options/App.vue)、[サイドパネル](../entrypoints/sidepanel/App.vue)、[wxt.config.ts](../wxt.config.ts)。

1. 開発ビルドではlocalhostを設定でき、本番ビルドでは会社用HTTPS URLを固定する。
2. 本番では任意のAPI接続先へ認証情報を送れないようにする。開発用トークン・接続設定を本番UIから外す。
3. 拡張からGoogleログインを行い、IAPが受け付ける認証情報を取得する方式を実証する。
4. 有効期限、更新、失効、アカウント変更、ログアウト、再認証を扱う。
5. 401/403、IAPのHTML応答・リダイレクト、ネットワークエラーを区別する。
6. 未認証・利用不可の間はAI実行を開始せず、実行中の認証失効でも後続操作を止める。

本番UIに求める状態:

| 状態 | 動作 |
| --- | --- |
| 認証確認中 | 状態を表示し、Runを有効にしない |
| 未ログイン | 会社アカウントでのログインを案内 |
| 認証・利用許可あり | 利用者を表示し、Runを使える状態にする |
| 権限なし | 利用不可と必要な社内対応を表示 |
| 期限切れ | 後続操作を止めて再認証を案内 |
| 通信失敗 | 接続失敗として表示し、認証エラーと区別 |

これらの本番状態のUIは未実装。アイコンでサイドパネルを開く動作と、会社APIへ認証して作業できることを分ける。

通常タブでGoogleへログイン済みであること、`chrome.identity.getAuthToken` で何らかのトークンを取得できることだけでは、IAPにそのまま接続できるとは仮定しない。選んだtoken種別、audience、OAuth client、拡張IDを合わせて実証する。拡張にOAuth client secretやサービスアカウント鍵を埋め込まない。[IAPのprogrammatic authentication](https://docs.cloud.google.com/iap/docs/authentication-howto) を基準にする。

## 4. 本番APIの認証と入口

対象: [index.ts](../server/index.ts)、[auth.ts](../server/auth.ts)、[app.ts](../server/app.ts)。

- 開発・本番の起動経路を分ける。本番でLOCAL_ROLE、LOCAL_EMAIL、dev-tokenを認証根拠にしない。
- 既存のIAP JWT検証関数を本番リクエスト経路へ組み込み、署名、issuer、audience、有効期限、必須claimsを確認する。
- 単一ドメイン判定を会社のWorkspace構成に合わせる。利用者の不変なIDを監査・利用量との関連付けに使う。
- 平文メールヘッダーを本人確認の根拠にしない。管理者権限もAPIで検証する。
- IAPを迂回するURLや未保護の入口からAPIへ到達できないことを実証する。
- CORSは本番の固定拡張IDへ絞り、認証の代わりとして扱わない。
- preflight、許可ヘッダー、IAP側の設定を採用構成で検証する。

Cloud RunへのIAP直接設定とロードバランサーでの設定を混在させず、採用方式を決める。[Cloud RunのIAP構成](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)、[署名付きヘッダー検証](https://docs.cloud.google.com/iap/docs/signed-headers-howto) を参照。

## 5. Cloud Runへ配置できるサーバーにする

現状、サーバー用Dockerfile、デプロイ設定、CI/CD、IaCは用意していない。ルートの `.devcontainer/` は開発用で、本番イメージではない。

必要な作業:

- Node.jsサーバー用イメージと起動コマンドを用意する。現在はtsxで起動し、tsxはdevDependenciesにあるため、本番での依存配置またはコンパイル方式を決める。
- 拡張のWXTビルドとサーバーのビルドを分ける。
- `.env`、`.data`、個人のADC、サービスアカウント鍵をイメージに含めない。
- 本番コンテナは `0.0.0.0` とCloud Runの `PORT` で待ち受ける。
- 必須の認証・ストア・モデル設定がない場合、開発用権限へフォールバックしない。
- 最大本文サイズ、モデル要求とCloud Runのタイムアウト、メモリー、同時実行数、最大インスタンス数を検証する。
- デモCRMと模擬プランの本番公開範囲を決める。

コンテナのファイルシステムを設定の永続保存先には使わない。待受とストレージの条件は [Cloud Runのコンテナ実行契約](https://docs.cloud.google.com/run/docs/container-contract) を参照。

## 6. Gemini用サービスアカウント

対象: [model.ts](../server/model.ts)。

モデルアダプターには `AI_PROVIDER=vertex`、`VERTEX_AUTH=metadata` の経路がある。Cloud Runに会社管理の実行用サービスアカウントを割り当て、承認済みモデルを利用するための必要最小限の権限を付ける。デプロイする人、IAPを使う社員、モデルを呼ぶ実行主体を分ける。

| 現在実装されている設定項目 | 本番での扱い |
| --- | --- |
| `AI_PROVIDER` | 主経路は `vertex` |
| `AI_MODEL` | 会社で利用を確認したモデルID |
| `GOOGLE_CLOUD_PROJECT` | モデル利用プロジェクト |
| `GOOGLE_CLOUD_LOCATION` | 承認済みのリージョン・データ所在地 |
| `VERTEX_AUTH` | `metadata` 経路を実証 |
| `PORT` / `HOST` | Cloud RunのPORT、待受は0.0.0.0 |

IAP audience、管理者一覧、共有ストア接続先などの本番設定は、起動コードへの読み込みが未実装。環境変数名と検証方法を新たに定める。開発用 `.env.example` を本番設定としてそのまま使わない。

本番でgcloudの個人ログインや秘密鍵の配布に頼らず、実行環境のサービスIDを使う。[Cloud RunのサービスID](https://docs.cloud.google.com/run/docs/securing/service-identity) を参照。

## 7. 共有ストア・監査・利用上限

対象: [store.ts](../server/store.ts)、[app.ts](../server/app.ts)、[contracts.ts](../src/shared/contracts.ts)。

現在の `.data/policy.json` とプロセス内の保存キューは単一プロセスの開発用。Firestore、Cloud SQL等の共有永続ストアへ置き換え、複数インスタンスのrevision競合をトランザクションで検出する。管理設定の保存先と、将来取得結果を保存する業務DBは別の用途として設計する。

追加する機能:

- 管理者指定、サイト・AI送信許可、一時解除、上限変更の監査。
- 利用者別のAPI・モデル利用量、同時タスク数、時間・費用の上限。
- インスタンスを増やしても迂回できない共有の制限。
- ストア・認証の障害時に、後続操作やモデル要求を止める扱い。
- 内容が不要なログにページ本文・指示・取得値・認証情報を残さない運用。

`maxSteps` / `maxMinutes` は主に拡張内の実行制御であり、社員別の厳密な利用量をサーバーだけで保証するものではない。改変クライアントに対してサーバーでどこまで強制するかも定める。

## 8. データ送信ルールと配布

サイト単位の操作・AI送信許可は実装済み。部署・業務・データ種類に応じた分類は未実装。本文、要素名、URLのクエリ、操作結果、作業メモの送信条件を決め、条件に合わないデータを送らない処理を追加する。

端末内履歴は最大20実行分で、会社の保管・削除ルールとの整合も確認する。スクリーンショット・任意スクリプトをモデルへ公開しない既存の制約を維持する。

本番配布では固定の拡張IDと会社承認済みの配布・更新経路を用意する。debugger、HTTP(S) host permissions等を、ChromeOSを含む管理対象Chromeで確認する。社員向けの更新とロールバック手順も整備する。

## 9. 作業順序と完了条件

| 段階 | 完了条件 |
| --- | --- |
| A. 会社環境で開発確認 | Workstationsと会社PCのChromeで、実モデルによる要約・URL調査・停止を確認 |
| B. 認証の最小実証 | 固定拡張IDからIAP経由APIへアクセスし、未認証・権限なし・期限切れも確認 |
| C. 本番API実装 | 本番起動、IAP検証、管理者権限、共有ストア、実行用サービスアカウントを接続 |
| D. ステージング | 本番と同じ認証方式で実拡張・実モデル・複数インスタンスを確認 |
| E. 社内配布 | 認証・データ・利用量・更新と切り戻しの条件を満たして段階的に配布 |

本番公開前の確認項目:

- [ ] dev-tokenやLOCAL_ROLEを本番の認証根拠にしていない。
- [ ] IAPの未認証・権限なし・期限切れで、UIの案内とAPI拒否が一致する。
- [ ] IAPを迂回する入口がない。
- [ ] 管理者以外は管理設定を変更できない。
- [ ] 操作許可とAI送信許可の取り消しを実行中にも反映する。
- [ ] 共有ストアが再起動・複数インスタンス・競合更新に対応する。
- [ ] 承認済みモデル・リージョン・サービスアカウントで動く。
- [ ] 認証失効、通信切断、未知の操作結果、拡張再起動で意図しない操作を再送しない。
- [ ] 必要な言語、検索・関連リンク・ページ送り・回答・保存を実Chromeで確認する。
- [ ] 利用量・費用・監査・ログの取り扱いが決まっている。
- [ ] 拡張とサーバーの更新・切り戻し手順がある。

この資料作成時点では会社環境での完了を確認していない。実施条件と結果を [validation.md](validation.md) に記録する。

## 10. MCP / Cloud SQLを後から追加する場合

現在の公開ツールはブラウザ操作・作業メモ・完了だけで、MCP接続やDB保存はない。必要になったら追加するもの:

1. サーバー側のMCPクライアント、または既存保存APIの呼び出し。
2. AIに公開する保存ツールと入力スキーマ。
3. 拡張で実行するツールとサーバーで実行するツールの振り分け。
4. 利用者にひもづく保存権限、DB接続、入力検証、監査。
5. 再送による二重保存を防ぐ冪等性と保存結果の確認。

応答スキーマと許可ツールがブラウザ用に固定されており、MCPのURLを設定するだけでは動かない。保存先と用途を確定し、エージェントとサーバーの通信契約も更新する。MCP / 業務DB保存は、調査・要約機能の本番提供に必須とはしない。
